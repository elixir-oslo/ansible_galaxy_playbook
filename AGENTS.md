# AGENTS.md — Galaxy Ansible Playbook

## Project Overview
Ansible-based deployment toolkit for [Galaxy](https://galaxyproject.org/) (`release_26.0`) with PostgreSQL 16, Gravity/Gunicorn, and Nginx on Debian/Ubuntu targets. The control node can be macOS or Linux; the deployment target must be Linux.

---

## Single Source of Truth
**`group_vars/galaxyservers.yml`** is the only file you need to edit before deploying. It contains two sections with different purposes:
- **Top block** (`galaxy:`, `database:`, `admin:`): consumed by `deploy.sh` via `yq` to auto-generate the `hosts` inventory file.
- **Lower block** (all `galaxy_*` / `postgresql_*` / `miniconda_*` vars): consumed directly by Ansible roles and tasks in `galaxy.yml`.

Do **not** manually edit `hosts` — it is auto-generated by `deploy.sh`.

---

## Critical Pre-Deploy Configuration
```yaml
# group_vars/galaxyservers.yml — edit these before running:
galaxy:
  host_ip: "1.2.3.4"        # Target VM IP or hostname
  ssh_user: "ubuntu"

database:
  password: "CHANGE_ME_STRONG_PASSWORD"

admin:
  email: "admin@example.com"
```

## Developer Workflows

### Full deployment (recommended)
```bash
./deploy.sh   # interactive menu → choose 1 for full_remote
```

### Step-by-step remote flow
```
2 → Prepare venv (python3 -m venv + pip install ansible yq)
3 → Install roles (ansible-galaxy install -r requirements.yml --force)
4 → Test SSH (ansible galaxyservers -m ping)
5 → Deploy (ansible-playbook galaxy.yml --flush-cache)
6 → Validate API
```

### Syntax check only (no SSH required)
```bash
source venv/bin/activate
ansible-playbook -i hosts galaxy.yml --syntax-check
```

### Post-deploy validation on the server
```bash
# Run on the target host:
bash devops-scripts/validate_galaxy.sh
# Checks: galaxyctl status, ports 8080/80, internal/external API, PostgreSQL vs SQLite, restart resilience
```

## Architecture: Three-Play Sequence in `galaxy.yml`
| Play | Hosts | Role/Action |
|------|-------|-------------|
| 1 | `galaxyservers` | Install PostgreSQL 16 |
| 2 | `dbservers` | Create Galaxy DB + user (`become_user: postgres`) |
| 3 | `galaxyservers` | Deploy Galaxy + Miniconda; nginx managed manually in post_tasks |

> `dbservers` aliases `galaxy` host in remote mode and `localhost` in local mode — both groups always point to the same machine.

## Key Design Decisions

### Client build is intentionally bypassed
The `galaxyproject.galaxy` role is invoked with a triple-lock to prevent Yarn/npm builds:
```yaml
galaxy_build_client: false
galaxy_skip_client_build: true
galaxy_client_use_prebuilt: true
galaxy_manage_node: false
```
Galaxy fetches prebuilt client assets via `GALAXY_INSTALL_PREBUILT_CLIENT=1`. Do **not** remove these flags — they prevent multi-minute or failing client builds.

### `galaxyproject.nginx` role is disabled
The role expects a Jinja2 template (`templates/nginx/galaxy.j2`) on the controller that is not present. Nginx config is written directly in `post_tasks` via `copy` with inline content. The vars `nginx_servers`, `nginx_profiles`, etc. in `group_vars/galaxyservers.yml` are vestigial; the live config lives in the `post_tasks` block of `galaxy.yml` (~line 291).

### Node.js IPv4 fix
`NODE_OPTIONS=--dns-result-order=ipv4first` is injected into `/etc/environment` and `/etc/profile` in pre_tasks to prevent DNS resolution failures in IPv6-preferred environments.

## Service Paths on Target
| Service | Path |
|---------|------|
| Galaxy root | `/srv/galaxy` |
| Galaxy server code | `/srv/galaxy/server` |
| Config | `/srv/galaxy/config/galaxy.yml` |
| Logs (Gravity/Gunicorn) | `/srv/galaxy/mutable/gravity/log/gunicorn.log` |
| Conda/Micromamba | `/srv/galaxy/mutable/dependencies/_conda` |
| Galaxy venv | `/srv/galaxy/venv` |

Gunicorn binds to `127.0.0.1:8080`; Nginx proxies port `80` → `8080` with a `10G` upload limit.
